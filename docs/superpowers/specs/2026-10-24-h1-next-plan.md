## 1.5 GPT 설계 검토 반영 (2026-10-24, gpt-6-astra) — 위 표를 대체하는 부분

**순서 변경:** 메뉴 목표("진도 읽기 + 다음 주문 지정")에 필요한 것은 알림·명령·읽기뿐이다. **H1-d → H1-c → H2 를 먼저** 끝내고, H1-a(스캔)·H1-b(트리 작업)는 메뉴와 별개로 나중에 한다. 트리 소속 조회는 이미 `IsTreeSpell` 이 있다(검증에 `IsSpellAvailableToLearn` 을 쓰면 안 됨: 기록 유무를 소속으로 착각).

**H1-d 정정:**
- 알림이 상태보다 먼저 나가는 곳은 3곳보다 많다: 같은 학파 교체의 Cleared(`Targets:36`), Set 알림이 prerequisites 저장·progress 생성·재부여보다 먼저(`Targets:47`), `MarkMastered` 의 알림이 `unlocked=true` 보다 먼저(`XP:362`), early 제거의 available 알림이 대상 삭제보다 먼저(`HookGrant:124` ↔ `Targets:95`).
- 규칙을 둘로 나눈다: (a) 상태 변경을 모두 끝낸 뒤 알림을 보낸다, (b) 그러나 **알림끼리의 순서**(drop/clear → set/grant → 최종 unlocked)는 그대로 지킨다. 패널 JS 는 이 순서에 의존한다(`progressionUI.js:797`, `cppCallbacks.js:569`).
- `ProgressionNotify` 에 시험용 관측 지점을 둔다: 알림마다 (이벤트, 그 순간의 상태)를 기록할 수 있어야 Prisma 없이 자가 테스트가 된다. 패널 표시 필터(숨김 시 progress·ready 생략)는 UIManager 쪽에 그대로 둔다. 큰 이벤트 버스는 만들지 않는다.

**H1-c 정정:**
- 학습 대상·습득을 바꾸는 경로는 패널 수동·자동 선택, 패널 해제(학파+formId), 일반 마법책, ISL 마법책(대상→대기→ISL 위임), 옛 ISL/DEST(경험치 뒤 대상), Papyrus 지정·raw 학파·학파별/전체 해제, 공개 API v2, 일반 unlock, 자동 마스터·ISL 완료, cheat·vanilla 습득·relock, early 지급·재지정·로드 재부여, co-save 복원·정규화·초기화.
- 하나의 검증으로 전부 바꾸면 동작이 바뀐다. **세이브 복원·정규화는 지금의 배치 적용으로 남긴다.** `LearningCommands` 는 "사용자 의도" 명령(패널 선택·해제, 메뉴 모드, Papyrus, API v2)만 받는다. 마법책·ISL 경로는 각자 의미를 유지하고 공통 기본 동작만 같이 쓴다.
- 명령 서명에 패널이 보내는 prerequisites, formId 기준 해제를 포함한다. single 모드 정리는 지금 경로마다 다르다(패널: 같은 학파까지 모두 Clear 후 Set / 마법책: 다른 학파만 Clear / Papyrus raw: 정리 없음). 각 경로의 현재 의미를 그대로 유지하고, 메뉴 모드는 패널 의미를 따른다.
- 패널 JS 의 정리 코드를 줄이려면 C++ 이 "지워진 학파 키와 주문"까지 알려야 한다(지금 clear 알림은 노드 상태만 바꿈). 줄이지 못하면 JS 는 그대로 둔다.
- 명령은 game thread 전용, 결과(성공/거절과 이유)를 돌려준다. 공개 API v2 의 Set/Clear(void, 직접 실행) 경로도 이 입구를 거치게 할지 함께 정한다.

**H1-a·H1-b 정정 (나중 단계):** catalog 후보를 후처리에 직접 넘겨야 한다(지금 PerkAdapters·SpellResearch 는 파일을 다시 읽음). Papyrus RunScan 의 동기 반환 계약 유지. 트리 생성의 최신 요청 보관은 지금 JS 가 하므로 그 소유를 먼저 정한다. 세이브 경계 정책(AutoBuild 의 "진행 단계는 끝내고 다음 단계만 보류")을 따로 정한다.

**시험 정정:** co-save 바이트 비교 대신 레코드를 풀어 키별로 정렬해 비교하고, runtime requiredXP·prerequisites·실제 습득·early 추적·알림 순서를 함께 본다. H2 는 "기록 없음 / 기록된 0% / 트리 밖 기록 / 실제 습득"을 구분하는 기대값 검사를 넣는다.

**M0 범위 조정:** 확장 지점(`GetExtensions()`)과 listener 33개 전체 대응은 메뉴 연결의 선행조건이 아니다. 먼저 작은 조회·명령 계약으로 메뉴 연결을 검증하고, 확장 구조는 4단계 직전에 설계한다(사용자 요구인 "4단계를 붙이기 쉽게"는 그때 첫 사용 예와 함께).
