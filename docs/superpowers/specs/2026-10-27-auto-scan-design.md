# 새 모드 감지 시 자동 스캔 — 설계 메모

날짜: 2026-10-27. 상태: 구현됨 (사용자 승인 2026-10-27, 커밋 f6b6b24e 이후; 결함 수정 8.7). 게임 안 확인 전. 브랜치 `feature/auto-scan` (기준 `release/1.6`).

## 한 줄 요약

게임을 켰을 때 로드 오더가 지난 스캔 때와 다르면, 메인 메뉴에서 스캔을 혼자 돌려 **카탈로그(`spell_catalog.json`)와 스캔 출력(`spell_scan_output.json`)만** 새로 만든다. 트리 파일과 학습 진행은 건드리지 않는다. 게임 스레드에서 하는 일은 아주 작은 조각으로 나눠 화면이 멈추지 않게 하고, 멈춘 시간을 재서 로그에 PASS/FAIL로 남긴다.

## 2. 스레드 모델

```
메인 메뉴 처음 뜸 ──▶ [대기 스레드] 톰 도달 패스 끝날 때까지 대기(최대 30 s)
                         │
                         ▼
             [게임 스레드] 조건 확인 → 잠금 획득
                         │
                         ▼
             [게임 스레드] 주문 수집, 한 번에 N개씩 조각 작업
                (조각마다 SKSE 작업 1개, 조각 사이에 화면이 그려짐)
                         │
                         ▼
             [작업 스레드] 글자로 바꾸기 → ClassifyScan(카탈로그 쓰기)
                           → spell_scan_output.json 쓰기 → 스캔 기록 쓰기
                         │
                         ▼
             [게임 스레드] 잠금 해제, 로그 한 줄 (게임 폼은 안 씀)
```

- **수집 조각내기.** `ScanSpellsToJson`의 주문 반복문을 "시작 번호~끝 번호"로 나눈다. 조각마다 폼 배열을 다시 가져와 범위를 확인한다(배열이 늘어날 수 있음). 조각 사이에는 `SpellItem*`를 들고 있지 않고 FormID만 들고, 다음 조각에서 FormID로 다시 찾는다(`kept`가 지금은 포인터를 들고 있음, `SpellScannerScan.cpp:29`). 반복문 뒤의 표시 작업(게이트·중복·톰 도달)과 `BuildScanOutput`은 먼저 시간을 재고, 한 조각 예산을 넘을 때만 나눈다. 조각 크기는 시간 예산(기본 4 ms)으로 정한다.
- **한 프레임에 조각 하나.** SKSE 작업 큐가 같은 프레임 안에서 새로 넣은 작업까지 돌리는지는 확인되지 않았다(`docs/librarian/ToDo.md` S-3). 그래서 조각마다 엔진의 프레임 시각(`RE::GetDurationOfApplicationRunTime()`, 프레임마다 바뀌는 엔진 시간값)을 적어 두고, 다음 조각은 그 값이 바뀐 뒤에만 돈다. 같은 값이면 실행하지 않고 대기 스레드가 1 ms 뒤 다시 올린다. 다음 조각을 올리는 것은 게임 스레드가 아니라 대기 스레드다.
- **결과는 같아야 한다.** 조각낸 수집의 JSON은 한 번에 수집한 것과 바이트 단위로 같아야 한다(타임스탬프 제외). 자가 테스트에서 비교한다.
- **퍼크 어댑터는 자동 스캔에서 부르지 않는다.** 게임 폼을 쓰고 게임 스레드에서 약 1.3 s 걸린다. 다음 게임 시작(kDataLoaded, 로딩 중)에 새 카탈로그 파일로 적용된다. **결과: 새 주문은 퍼크 모드 키워드를 다음 게임 시작부터 받는다** (결정 3).
- **Spell Research.** 부르지 않는다: 세이브를 불러올 때 파일을 다시 읽는다(`OnGameLoaded`). 카탈로그를 쓰기 **전에** 세이브 불러오기가 끝났다면 그 세이브에서는 옛 카탈로그 그대로이고, 다음 세이브 불러오기에 새 것을 읽는다(로그에 남김). (구현 리뷰 반영: 그 자리에서 `OnCatalogChanged`를 부르면 게임 중에 Spell Research 목록을 쓰고 게임이 멈출 수 있어 뺐다.)
- **세이브 경계 (세대 번호).** 세이브 불러오기·새 게임(kPreLoadGame·kNewGame)마다 세대 번호를 올린다. 수집 조각은 시작 때의 세대와 다르면 멈추고 결과를 버린다: 다음 메인 메뉴에서 다시 시도한다. 수집이 끝나 작업 스레드로 넘어간 뒤면 끝까지 간다(게임 폼을 안 읽음). 이때 세대가 바뀌었으면 위의 Spell Research 동기화를 한다.
- **다른 스캔과의 관계.** 패널 스캔이나 Papyrus 스캔이 도는 중이면 자동 스캔은 시작하지 않고 다음 메인 메뉴로 미룬다. 자동 스캔 중에 플레이어가 패널 스캔을 누르면 패널 스캔은 지금처럼 대기열에 들어가 자동 스캔 다음에 돈다. Papyrus RunScan은 잠금을 안 쓰는 지금 그대로다(카탈로그 만들기는 `ClassifyScan`이 스스로 한 번에 하나로 막음).
- **`spell_scan_output.json` 쓰기 잠금.** 패널의 Save 버튼과 공유한다. 작업 스레드가 10-20 MB를 쓰는 중에 Save를 누르면 그만큼 기다린다. 드물어서 그대로 둔다.

## 3. 언제 도나 (트리거)

모두 맞을 때 게임 시작마다 한 번:

1. 설정 `autoBuild`가 "off"가 아니다 (config.json을 C++이 직접 읽음, 읽지 못하면 돌지 않음).
1-1. 트리가 있다(`spell_tree.json`에 주문이 있음). 트리가 없거나 비었으면 패널의 자동 빌드(`whenMissing`)가 전체 스캔을 하므로 자동 스캔은 비켜 준다. 그 스캔이 카탈로그를 만들면 스캔 기록도 남는다. 같은 메인 메뉴에서 스캔이 두 번 돌지 않는다.
2. 현재 로드 오더 지문 ≠ 마지막으로 카탈로그를 만든 스캔의 지문.
3. 이번 세션에 이미 카탈로그를 만든 스캔이 없다.
4. 다른 스캔이 돌고 있지 않다.

**스캔 기록 파일.** `spell_catalog_loadorder.json`(카탈로그 옆). `{ version: 2, loadOrder, scan, tomeReach, plugins, spells, catalogBytes, catalogHash, rules }` (8.7 이후 모양; 비교는 `scan`으로 한다). 트리 기록 파일과 따로 둔다: 트리 기록을 쓰는 함수는 아는 칸만 써서 새 칸을 지운다.

- **전체 범위("all") 스캔이 카탈로그를 실제로 새로 쓴 경우만** 기록한다: 자동 스캔, 패널 전체 스캔, Papyrus `RunScan("all", ...)`. 그러려면 `ClassifyScan`이 "새로 썼다/안 썼다"를 돌려줘야 한다(작은 시그니처 변경, 오프라인 하네스도 같이 수정).
- **책 범위("tomes") 스캔이 카탈로그를 새로 쓰면 기록을 지운다.** 지금 Papyrus `RunScan("tomes", "full")`은 효과 정보가 있어 책이 가르치는 주문만으로 카탈로그를 덮어쓴다(`SpellScannerJson.cpp:426-445`, `LibrarianCatalog.cpp:321-347`). 이 경우 다음 시작에 자동 스캔이 전체로 다시 만든다. (그 덮어쓰기 자체가 맞는지는 이번 범위 밖, 따로 보고.)
- 기록에는 카탈로그 파일의 크기와 FNV-1a 64도 넣는다. 다음 시작에 카탈로그가 기록과 다르면(다른 길로 바뀜) 기록이 없는 것으로 본다.
- 지문은 수집할 때(게임 스레드) 잡아서 작업 스레드로 넘긴다. `CurrentLoadOrder`는 스레드 안전하지 않다.
- **규칙 지문.** 기록에 카탈로그 버전과 분류 규칙 파일(`librarian/`)의 FNV도 넣는다. 업데이트로 규칙이 바뀌면 로드 오더가 같아도 다시 돈다(구현 리뷰 반영).
- **이미 설치한 사람.** 스캔 기록이 없으면 한 번 돈다. 트리 기록으로 추정하지 않는다: 트리 기록은 카탈로그를 제대로 썼다는 증거가 아니다(`UIManagerTree.cpp:301-305`, `LibrarianTraits.cpp:230-244`). 업데이트 후 첫 시작에 한 번 돌고, 이후로는 로드 오더가 바뀔 때만 돈다.
- **안내 문구.** 기존 HUD 안내 `hud.loadOrderChanged`("트리를 다시 만들면 새 주문이 들어갑니다")는 그대로 둔다. 자동 스캔은 트리에 넣지 않으므로 그 말은 여전히 맞다. 새 문구는 추가하지 않는다.

## 4. 트리·진행 상태를 건드리지 않는다는 보장

- 자동 스캔 경로가 쓰는 파일은 셋뿐: `spell_catalog.json`, `spell_scan_output.json`, `spell_catalog_loadorder.json`. 그리고 주문 카드용 메모리(`g_cardElements`).
- 부르지 않는 것: `SaveSpellTree*`, `RecordTreeLoadOrder`, `ValidateAndFixTree`, `ProgressionManager`, 패널 호출(`CallView`), `PerkAdapters::Apply`, `SpellResearchPatch::*`.
- 정적 검사: 새 파일(`AutoScan.cpp`)에 위 이름이 없음을 grep으로 확인.
- 자가 테스트: 시작 전·후 `spell_tree.json`, `spell_tree_loadorder.json`의 FNV가 같음 → PASS/FAIL. 진행 상태는 메인 메뉴에 없고, AutoScan.cpp는 진행 헤더를 포함하지 않는다(정적 확인).
- 진행 쪽 파일(ProgressionManager*, SpellEffectivenessHookGrant, SpellTomeHook, ISLIntegration)과 `h1-core-state` 워크트리는 건드리지 않는다.

## 5. 히치(화면 멈춤) 재는 방법

- **주 지표: 실제 프레임 길이.** 감시 스레드가 2 ms마다 작은 작업을 게임 스레드에 올리고, 작업은 엔진 프레임 시각(`GetDurationOfApplicationRunTime`, ms)을 적는다. 값이 바뀐 지점 사이의 차이 = 프레임 하나의 길이. 그 최댓값이 "가장 긴 프레임"이다. 조각과 감시 작업이 한 프레임에 몰려 돌아도 그 프레임 전체 길이가 잡힌다.
- **보조 지표.** 작업 대기 시간(실행 시각 − 올린 시각)의 최댓값, 조각별 실행 시간, 조각 수 = 서로 다른 프레임 시각 수(한 프레임에 조각 하나가 지켜졌는지).
- **기준선.** 스캔 시작 전 3초 동안 같은 방법으로 메인 메뉴의 평소 가장 긴 프레임을 잰다.
- **판정.** 스캔 중 가장 긴 프레임 ≤ 기준선 + 예산(기본 25 ms), 그리고 조각마다 프레임이 달랐으면 PASS. 프레임 시각을 읽을 수 없으면(VR 주소 등, 확인 필요) SKIP. 예산과 조각 시간은 `selftest.json`에서 바꿀 수 있다.
- **로그.** `AutoScan: hitch baseline max N ms, during scan max N ms (slice budget 4 ms, N slices) - PASS/FAIL`, 조각별 최장 시간과 그 단계 이름(수집/표시/출력)도 남긴다.
- 감시 스레드는 자가 테스트가 켜졌을 때만 돈다. 일반 플레이에서는 조각별 시간만 로그에 남긴다.

## 6. 자가 테스트 (selftest.json, 개발 설치만)

| 검사 | PASS 조건 |
|---|---|
| 자동 스캔 실행 | 지문이 달라지게 꾸민 기록에서 시작 → 카탈로그·스캔 출력·스캔 기록이 새로 쓰임(수정 시각, 기록 지문 = 현재) |
| 트리·진행 불변 | 위 4절의 해시 비교 |
| 최대 정지 시간 | 5절 판정 |
| 조각 수집 = 한 번 수집 | 같은 설정으로 두 방식 JSON 비교(타임스탬프 제외) |
| 두 번째는 안 돎 | 기록이 현재와 같으면 "skipped - load order unchanged" 로그 |
| 세이브 경계 | 조각 수집 중 세대 번호를 강제로 올리면 수집이 버려지고 파일이 안 바뀜 |
| 트리 없는 시작 | 트리 상태가 missing/empty면 "left to the panel's build" 로그, 자동 스캔 안 돎 |

오프라인: 기존 `librarian-check`·`librarian-test`·패널 테스트가 PASS (ClassifyScan 시그니처 변경 확인). 빌드 경고 0.

## 7. 사용자에게 남는 확인 (눈으로만 판단 가능)

- 로드 오더를 바꾸고 게임을 켰을 때, 메인 메뉴에서 마우스·메뉴 움직임이 끊기지 않는가. 로그의 PASS가 숫자로 보증하지만, "끊겨 보이는지"는 사람 눈으로만 판단된다.

## 8. 결정이 필요한 것

1. **결정 1:** B(지금 붙이기) — 추천.
2. **결정 3:** 새 주문의 퍼크 모드 키워드를 (a) 다음 게임 시작부터(추천, 멈춤 없음) / (b) 이번 세션에 바로(약 1.3 s 멈춤, 피하려면 카탈로그 읽기를 작업 스레드로 옮기는 추가 작업 필요).
3. 스캔 출력 파일을 늘 쓸지: 지금 패널 스캔은 개발 설치에서만 `spell_scan_output.json`을 쓴다. 자동 스캔은 Papyrus 스캔처럼 늘 쓴다(요구사항 "스캔 출력 갱신").

## 8.5 GPT 설계 검토 반영 (gpt-6-astra, 2026-10-27)

5건 모두 코드로 확인해 반영했다. (1) 책 범위 Papyrus 스캔에 완료 기록을 주던 문제 → 전체 범위만 기록, 책 범위가 덮어쓰면 기록 삭제. (2) 세이브를 불러온 뒤 카탈로그가 써지면 Spell Research가 놓치는 문제 → 세대 번호로 감지해 동기화. (3) 작업 대기 시간만으로는 화면 멈춤을 보증 못 함 → 엔진 프레임 시각으로 실제 프레임 길이 측정, 한 프레임에 조각 하나. (4) 트리 없는 시작에서 스캔이 두 번 도는 문제 → 패널 자동 빌드에 맡김. (5) 트리 기록으로 스캔 기록을 추정하던 것 → 삭제, 업데이트 후 한 번 돈다.

## 8.6 게임 안 첫 실행 반영 (2026-10-27)

메인 메뉴 뒤 약 13초 안에 세이브를 불러오면 그 세션에 스캔이 돌지 않았다(세대 번호를 메인 메뉴 때 잡음, 대기 단위 10초). 사용자 승인으로 고침: 세대 번호는 폼 읽기를 시작할 때 잡는다(게임 중에도 조각으로 돈다), 읽는 도중 불러오기가 끼면 끝난 뒤 바로 다시(최대 3번), 기다리는 동안 250 ms마다 세대 확인, 끝나지 못해도 자가 테스트 RUN FAIL 줄.

## 8.7 결함 수정 (2026-10-27)

게임 안 실행(13:34-13:42) 로그에서 세 가지 결함을 찾아 고쳤다. 자가 테스트 6개는 모두 통과했지만, 아래 문제는 그 테스트가 보지 않는 곳이었다.

1. **빠진 표시가 있어도 "다 했다"고 기록했다.** 책 도달 검사(어떤 책을 아무도 안 주는지 보는 작업)가 끝나지 않았거나 실패하면 스캔에 `tomeUnreachable` 표시가 없다. 그래도 스캔 기록을 남겨서, 다음 시작은 스캔을 건너뛰었다. 이제 스캔 출력 맨 위에 빠진 것의 목록 `incomplete`를 넣는다(`ScanRecordRules.h`, 수집기의 `Finish`). 카탈로그는 그대로 쓰지만(옛 것보다 낫다) 기록은 지운다. 그래서 다음 시작에 다시 스캔한다. 자동 스캔, 패널 전체 스캔, Papyrus `RunScan("all")` 세 길 모두 같다.
2. **흡혈귀 주문 모으기가 통째로 실패해도 모른 채 넘어갔다.** 로그 13:40:44 "could not collect the spells vampires cast". 이제 NPC 하나씩 따로 감싸서, 읽다가 망가진 NPC는 FormID를 로그에 남기고 건너뛴다(나머지는 계속 읽는다). 전체가 멈춘 경우만 "실패"로 보고(`SpellScanner::VampireCastersState`), 그 세션의 전체 스캔은 1번처럼 "빠진 것 있음"이 된다. NPC 몇 개를 건너뛴 것은 실패로 치지 않는다: 그러면 망가진 NPC가 있는 로드 오더는 매번 시작마다 스캔하게 된다.
3. **지문이 플러그인 이름과 주문 수만 봤다.** 같은 이름으로 업데이트한 모드, `gate/rules.json` 변경을 놓쳤다. 이제 스캔 기록은 따로 만든 "스캔 지문"(`LoadOrderFingerprint::Value::scan`)으로 비교한다: 기존 지문 + 플러그인마다 파일 크기와 마지막 수정 시각 + 게이트 규칙 파일 해시 + 스캐너 형식 번호(`kScannerFormatVersion`). 크기와 시각은 게임이 파일을 찾을 때 이미 적어 둔 값(`TESFile::fileData`)을 읽어서 파일을 열지 않는다. 그 값이 비어 있으면 파일마다 크기만 물어본다(로그에 어느 쪽인지 남김). 트리 기록(`spell_tree_loadorder.json`)은 기존 지문 그대로다: 같은 주문으로 다시 저장된 모드 때문에 "트리를 다시 만드세요" 안내가 뜨면 안 되기 때문이다. 기록 버전은 2로 올렸고, 버전이 다르면 맞지 않는 것으로 본다. 그래서 업데이트 뒤 첫 시작에 한 번 스캔한다.

자가 테스트: `RUN`은 "완전한 스캔이면 기록이 맞고, 빠진 것이 있으면 기록이 없다"로 바꿨다. `COMPLETE`를 새로 넣었다(흡혈귀 주문 모으기 상태와 빠진 것 목록, 하나라도 빠지면 FAIL). 오프라인 검사는 `librarian-test --self-test`에 17개 추가(`tools/scanrecord-selftest.cpp`).

**리뷰 반영 (같은 날).**
- 책 도달 검사가 매번 같은 이유로 실패하거나(읽을 수 없는 플러그인) 30초보다 오래 걸리는 로드 오더는 매 시작마다 스캔하게 되던 문제: 자동 스캔은 이제 시간 제한 없이 검사가 끝나길 기다린다(30초마다 "still waiting" 로그). 검사가 "실패"로 끝난 것은 빠진 것으로 치지 않고, 그 결과(`TomeReach::OutcomeKey`: 읽지 못한 플러그인 이름들의 해시)를 기록 지문에 넣는다. 같은 플러그인이 계속 실패하면 기록이 유지되고, 그 플러그인을 다시 읽을 수 있게 되면 다시 스캔한다. "아직 실행 중"일 때만 빠진 것이다(패널 스캔이 검사 도중에 돈 경우).
- 흡혈귀 주문 모으기: NPC 절반 넘게 건너뛰면 실패로 친다. 건너뛴 NPC는 처음 10개만 FormID로 로그에 남기고 나머지는 개수만 센다. 종족·템플릿 캐시는 결과가 다 나온 뒤에만 넣는다(중간에 오류가 나면 아무것도 남지 않아 다음 NPC가 다시 계산한다).
- 플러그인 크기·시각은 플러그인마다 정한다: `fileData`의 파일 이름이 그 플러그인과 같고 값이 0이 아니면 그것을, 아니면 그 파일만 stat한다. 로그에 각각 몇 개인지 한 줄.
- 기록을 지우는 이유가 정확해졌다: 책 스캔 / 로드 오더 모름 / 스캔 지문 모름(게이트 규칙을 못 읽음 또는 검사 실행 중) / 빠진 것 있음.
- 오프라인 검사 8개 추가(합 25): 기록 버전 확인(`RecordFits`), 책 도달 결과, 흡혈귀 실패 기준.
- 한계: 같은 이름으로 업데이트한 모드는 크기·시각 값으로만 알아챈다. 게임에서 그 값이 채워지는지는 위 로그 줄로 확인한다.

남은 확인(게임 안, 로그로 판정): `fileData`가 실제로 채워져 있는지(로그 `N from the engine's find data, N from the files on disk`), 건너뛴 NPC의 FormID, 흡혈귀 주문 모으기가 이제 끝까지 가는지, 모드 파일 하나의 수정 시각만 바꿨을 때 다음 시작에 스캔하는지.
